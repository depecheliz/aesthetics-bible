# Image-provider benchmark (Stage 1)

Standalone harness comparing three image-edit providers on identity
preservation, prompt adherence, realism, and cost. **Completely isolated
from the app** — no application code, Supabase table, Edge Function, or
service interface is touched by anything in this directory.

## Providers benchmarked (verified against Replicate's public docs/pricing on 2026-08-27 — not the earlier research report's numbers, some of which were stale)

| Provider | Replicate model | Verified/estimated cost |
|---|---|---|
| Nano Banana 2 (Gemini 3.1 Flash Image) | `google/nano-banana-2` | ~$0.08/image (estimate, from Google's direct API rate at 1K resolution — Replicate's exact flat rate wasn't published; the harness captures Replicate's own billing signal per call when available) |
| FLUX.1 Kontext [pro] | `black-forest-labs/flux-kontext-pro` | $0.04/image (confirmed on Replicate's pricing page) |
| InstantID (photorealistic) | `grandlineai/instant-id-photorealistic` | ~$0.017/run at typical ~18s runtime, billed as L40S GPU-seconds ($0.000975/sec) — the harness computes the real per-call figure from Replicate's reported `predict_time` |

Note: the original research report named the older `google/nano-banana`
(Gemini 2.5 Flash Image) and cited InstantID at ~$0.017–0.02 from a
secondary source. Re-verification for this benchmark found a newer,
higher-ranked model (`nano-banana-2`) and confirmed the InstantID cost is
GPU-time-billed, not a fixed $0.017 — this harness uses the corrected
model/pricing.

Exact input schemas were confirmed from Replicate's own docs/blog
examples where possible; anything not exercised against a live call yet
is flagged in `providers.js`. The harness logs each provider's first
raw response shape so a schema mismatch is obvious immediately, not 100
calls in.

## Setup

1. **Source portraits** — place exactly 3 image files (jpg/png/webp) in
   `inputs/`. This folder is gitignored; nothing here is committed.
2. **API token** — copy `.env.example` to `.env` in this same directory
   and set `REPLICATE_API_TOKEN` (create one at
   https://replicate.com/account/api-tokens). `.env` is gitignored.
   The token is read only into `process.env`, used only in the
   `Authorization` header of each request, and is never written to any
   log, output file, or manifest record.

## Running

```
cd benchmarks/image-providers
node run-benchmark.js --dry-run     # prints the full plan + cost estimate, calls nothing
node run-benchmark.js --confirm     # runs all generations for real — costs real money
node generate-scoresheet.js         # builds outputs/scoresheet.csv from the manifest
# ... review outputs/review.html, fill in the score columns in scoresheet.csv ...
node summarize-results.js           # per-provider pass rate + effective cost per accepted result
```

`run-benchmark.js` refuses to run the paid batch (`--confirm`) unless
exactly 3 source portraits are present.

## What gets produced (all gitignored under outputs/)

- `outputs/<source>/<mode_transformation>/<provider>/repeat_N.jpg` — every
  generated image.
- `outputs/manifest.jsonl` — one JSON record per generation attempt:
  provider/model, source id, transformation, intensity, repeat number,
  output file path, latency, cost (and whether it's provider-computed or
  an estimate), success/failure, error type, timestamp. No token, no raw
  image bytes, no base64 — file paths only.
- `outputs/review.html` — generated by `generate-review-page.js`, a
  local-only page (open via `file://`, never uploaded anywhere) grouping
  every output by source → transformation → provider for side-by-side
  comparison.
- `outputs/scoresheet.csv` — generated by `generate-scoresheet.js`, one
  row per generation with the manifest fields plus empty columns for you
  to fill in: `identity_preservation_pass_fail`, `prompt_adherence_1_5`,
  `unintended_changes_1_5`, `realism_1_5`,
  `consistency_between_repeats_1_5`, `human_acceptance_accept_reject`,
  `notes`.

## Scoring rule

Identity preservation is a hard gate. `summarize-results.js` only counts
a generation as "accepted" if `identity_preservation_pass_fail = pass`
**and** `human_acceptance_accept_reject = accept` — a cheaper model
cannot win by having a lower nominal price if it fails identity
preservation. The reported "effective cost per accepted result" is total
generation cost ÷ accepted count, which is the number that actually
matters for picking a production provider.

## Same-instruction rule

`transformations.js` defines one final instruction string per
transformation (4 Preview looks at Moderate intensity + 2 Glow presets),
used verbatim across all three providers. Each provider's `buildInput()`
in `providers.js` only changes which JSON field the instruction goes
into — never the wording. Do not edit a transformation's wording per
provider; that would invalidate the comparison.
